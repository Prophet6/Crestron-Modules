Remote File Sync v1.0

One symbol that checks a remote file, copies it onto the processor, or copies the processor file back over the remote one.

Start here

Remote File Sync v1.0 keeps one processor file matched to one remote file. Check asks whether the remote file exists. Retrieve downloads it and replaces the processor file. Overwrite uploads the processor file and replaces the remote file. Enable_Pull checks and retrieves on a timer. It never uploads. Enable_Push uploads on a timer. It never downloads.

SIMPL+ symbol

Remote File Sync v1.0 is the symbol you drop in SIMPL Windows. F1 on that symbol opens this page when this HTML file sits beside the .usp.

Library

Library RemoteFileSync_v1, source RemoteFileSync10142026.cs, class RemoteFileSync. The source file stays datecoded. The solution names the archive RemoteFileSync_v1.clz. Keep that .clz next to the .usp.

Processor

4-Series only. The module does not parse the file. File Reader still owns formats, encryption, and backups.

  1. Keep RemoteFileSync_v1.clz and this HTML file next to Remote File Sync v1.0.usp. The Simpl# source remains RemoteFileSync10142026.cs.
  2. Set Local_Path to the full processor path, extension included. Example: /user/boardroom.json.
  3. Set Remote_URL to one file. The scheme is http://, https://, or ftp://. Put the port in the URL when it is not the default.
  4. Leave Remote_User and Remote_Password empty for anonymous access, or fill both.
  5. Pulse Check, then Retrieve or Overwrite. Read Feedback after each pulse.

What it can reach

The remote location is a URL. The processor copies that one file onto a path it can already open. It does not mount a folder.

URLCheckRetrieve and overwrite
http://HEAD. A server that rejects HEAD is checked by a download that is then deleted.GET and PUT
https://HEAD, with the same fallback.GET and PUT over TLS
ftp://The file is downloaded to a temporary probe and the probe is deleted.RETR and STOR
A Windows share (\\server\share\file.json) and a cloud folder (OneDrive, SharePoint, Google Drive, Dropbox) are not paths this symbol can open. Publish that folder over HTTP, HTTPS, or FTP first.

Accepted processor paths are /user/file.json, \user\file.json, and \\user\\file.json. The transfer uses a path that starts with /. 4-Series paths are case-sensitive. /user/Boardroom.json and /user/boardroom.json are different files.

Inputs

One operation runs at a time. A pulse while Busy_FB is high is ignored. A non-empty serial replaces the parameter across from it. An empty serial leaves that parameter in charge.

SignalKindWhat it does
CheckDigital inRising edge asks whether the remote file exists. The processor file is not changed. Across from Remote_Exists_FB.
RetrieveDigital inRising edge downloads the remote file and replaces the processor file. The previous processor file is kept when the download fails. Across from Local_Exists_FB.
OverwriteDigital inRising edge uploads the processor file and replaces the remote file. The processor file is kept when the upload fails. Across from Busy_FB.
Allow_Insecure_TLSDigital inHigh skips HTTPS host and peer checks. Required for a self-signed certificate. Low keeps those checks on. FTP and HTTP ignore it. Across from Retrieved.

Enable_PushDigital inOn the row under Enable_Pull. While high, uploads the processor file. It never downloads. 0s pushes once. A greater time repeats. A missing processor file does not change the remote file.

Check, retrieve, overwrite

Check

HTTP and HTTPS send HEAD. A 2xx response means the file exists. 404 or 410 means it is absent. 401 or 403 means the login was rejected. A server that rejects HEAD, or that closes the connection before the status can be read, is checked by downloading the file to a temporary name and deleting that temporary file. The real processor file is not touched.

FTP check downloads to a sibling .probe file and deletes the probe. A missing file is reported from the server's 550 reply. The processor file stays as it was.

Retrieve

The download is written to Local_Path plus .part. On success the existing processor file is deleted and the part file is moved into its place. On failure the part file is deleted and the previous processor file remains. A file larger than 256 KB is discarded the same way.

Close the file in Toolbox before a retrieve that must replace it. An open view can deny the delete.

Overwrite

The processor file is uploaded to the same URL. Failure leaves that local file in place. Success pulses Overwritten. If the remote file is missing, the server may create it. That still counts as success when the upload returns success.

Pull and push

Hold Enable_Pull high to refresh the processor file from the remote file. Each cycle checks, and retrieves when the remote file exists. A missing remote file does not delete or rewrite the processor file. Dropping Enable_Pull stops the timer. A transfer that has already started is allowed to finish.

  • Pull_Interval at 0s pulls once when the level rises, and once after startup if the level is already high.
  • A greater time repeats while the level stays high. The wait is the parameter, unless Pull_Interval_Override is not 0.
  • The override is whole seconds. 10 is 10 seconds. 0 uses the parameter.

Hold Enable_Push high to refresh the remote file from the processor file. Each cycle uploads when the processor file exists. A missing processor file does not change the remote file. Dropping Enable_Push stops that timer. Push_Interval and Push_Interval_Override follow the same 0s and seconds rules as the pull interval.

Pull never uploads. Push never downloads. One transfer runs at a time, so a pull and a push that come due together take turns.

Login

Leave Remote_User empty for anonymous access. The password is ignored while the user is empty. Fill both fields when the server requires a login. A non-empty override replaces the matching parameter.

HTTP and HTTPS send Basic authentication on the first request. A wrong password is rejected. Feedback says Login was rejected and Remote_Exists_FB stays low. FTP sends USER and PASS. A wrong password is rejected before the file is transferred.

The password is stored in the SIMPL program. It is not written to Feedback or the error log.

HTTPS

A 4-Series processor does not speak TLS 1.3. The remote server must offer TLS 1.2. A server that offers only TLS 1.3 fails the handshake. Feedback may say HTTPS handshake failed, or No error on a program that has not been uploaded since that message was added. Some firmware still begins the handshake at TLS 1.0, so a server that accepts TLS 1.0 through 1.2 will meet more processors than one that accepts only TLS 1.2.

Host and peer checks stay on while Allow_Insecure_TLS is low. A self-signed certificate, including a bench certificate, needs that signal high. Low is the right setting when the processor already trusts the server certificate.

Put a non-default port in the URL: https://192.168.1.20:8443/boardroom.json.

File Reader

This module does not parse JSON, CSV, or any other format. When the file is a config that File Reader already understands, point both symbols at the same processor file and let File Reader read it after each download.

  1. Set Local_Path to the full path, for example /user/boardroom.json.
  2. Set File Reader's folder, name, and extension so they land on that same path.
  3. Wire Retrieved to File Reader Read.

An overwrite updates the remote copy of whatever is already on the processor. File Reader's write stays local until you pulse Overwrite.

Limits

  • 4-Series only. One operation at a time.
  • Downloads larger than 256 KB are discarded. The processor file is not replaced.
  • String parameters and overrides are 255 characters for the URL and the path, and 64 characters for the user and the password.
  • Pull_Interval and Push_Interval above 655.35s wrap, because each time is stored in a 16-bit count of hundredths of a second. The symbol still shows an upper bound of 3600s.
  • Pull_Interval_Override and Push_Interval_Override are analogs, so the largest value is 65535 seconds.
  • The transfer gives up after the client timeout. That timeout is passed as 15.

Examples

Refresh a JSON config

  1. Set Remote_URL to http://192.168.1.20/configs/boardroom.json.
  2. Set Local_Path to /user/boardroom.json.
  3. Pulse Check. Remote_Exists_FB goes high and Feedback says Remote file found.
  4. Pulse Retrieve. Retrieved pulses. Wire that pulse to File Reader Read.
  5. Hold Enable_Pull high and set Pull_Interval to 60s, or set Pull_Interval_Override to 60. The processor file refreshes about once a minute. The remote file is not uploaded.

Publish the processor file

  1. Edit /user/boardroom.json and close it in Toolbox.
  2. Hold Enable_Push high. Set Push_Interval to 0s for one upload, or set Push_Interval_Override to 30 to upload about every 30 seconds.
  3. Overwritten pulses after each successful upload. Feedback says Remote file replaced. The processor file is not replaced by the remote copy.

Self-signed HTTPS

  1. Set Remote_URL to https://192.168.1.20:8443/boardroom.json.
  2. Leave Allow_Insecure_TLS low and pulse Check. The check fails.
  3. Raise Allow_Insecure_TLS and pulse Check again. Feedback says Remote file found.

Push an edit back

  1. Edit /user/boardroom.json on the processor. Close it in Toolbox.
  2. Pulse Overwrite. Overwritten pulses and Feedback says Remote file replaced.
  3. Pulse Retrieve. The processor file matches the edit that was uploaded.

Reject a bad password

  1. Set Remote_User to the account and Remote_Password to a wrong password.
  2. Pulse Check. Remote_Exists_FB stays low.
  3. HTTP and HTTPS set Feedback to Login was rejected. FTP stops at the login and does not transfer the file.
  4. Clear Remote_User to try the same URL anonymously, or put the correct password back.
